## 0. 먼저 읽어야 할 전제

**이 매출 데이터는 실제 판매 기록이 아니라 합성 데이터(`data_type = synthetic_dummy`)이고, 날씨 효과가 생성 규칙에 이미 들어 있다.**

- `daily_generation_inputs.csv`에 기온 계수(`temp_factor`, 0.9265~1.0455)와 강수 계수가 있고, 이 값이 총주문 생성에 쓰였다.
- `docs/sales_dummy_v1_revision2_final_audit.md`에 HOT 선택 확률이 `p(HOT)=clip(1/(1+exp((avg_temp_c-16)/5)), 0.10, 0.95)`로 생성됐다고 기록돼 있고, "실제 관측 인과관계가 아닙니다"라고 명시돼 있다.

따라서 아래 결과는 **"실제 고객이 기온에 반응한다"는 증거가 아니다.** 이 분석이 확인하는 것은 "데이터에 들어 있는 기온 규칙을 모델이 복원해 예측 성능으로 바꿀 수 있는가"(파이프라인 검증)이다. 실제 POS 데이터가 들어오면 같은 스크립트로 다시 돌려야 결론을 낼 수 있다. 상관관계는 인과관계로 해석하지 않는다.

## 2. 분석에 사용된 행 수와 기간

- 기술 분석: 669일(2025-01-01 ~ 2026-10-31), 메뉴×일 18,063행
- 예측 검증: 시간순 확장 윈도우(expanding window), 월 단위 10개 폴드
  - 최초 학습: 2025-01-01 ~ 2025-12-31 (365일)
  - 검증: **2026-01-01 ~ 2026-10-31, 304일**, 메뉴×일 8,208행
  - 각 폴드의 학습 데이터는 해당 월 시작일 이전만 사용(코드에서 학습 마지막 날 < 검증 첫 날을 assert로 확인). 목표값의 과거값(lag)은 입력으로 쓰지 않았다.
- 날씨 입력은 **검증일의 실제 관측 기온**이다. 즉 "예보가 완벽히 맞는다"는 가정이므로 실제 운영에서 예보 오차가 있으면 이득은 이보다 작아진다.

## 5. 날씨 변수 추가 전후 예측 성능 (2026-01-01 ~ 2026-10-31, 동일 검증 기간)

모델: 푸아송 회귀(GLM, 기온은 스플라인), 보조로 그래디언트 부스팅(HGB, 푸아송 손실). 기준선은 "같은 요일 최근 8주 평균". 달력 변수(`cal`)는 요일·공휴일·연휴·연휴 전날·시험·방학이며, `cal+month`는 월 더미를 더한 것이다. 지표 WAPE는 낮을수록 좋다. 신뢰구간은 7일 블록 부트스트랩(2,000회)이다.

### 5.1 일 총 판매 수량 (304일)

| 모델 | WAPE | MAE |
|---|---|---|
| 같은 요일 8주 평균 | 15.38% | 10.96 |
| **GLM 달력(`cal`)** | **7.58%** | 5.40 |
| GLM 달력 + 평균기온 | 7.59% | 5.41 |
| GLM 달력 + 평균·최고·최저기온 | 7.59% | 5.41 |
| GLM 달력 + 월 | 8.02% | 5.72 |
| GLM 달력 + 월 + 평균기온 | 7.91% | 5.64 |
| GLM 달력 + 월 + 3기온 | 7.95% | 5.67 |
| HGB 달력 | 7.70% | 5.49 |
| HGB 달력 + 3기온 | 8.44% | 6.01 |

- **총 수량에서는 기온을 더해도 개선이 확인되지 않는다.** GLM 달력 기준 +0.01~0.02%p(오히려 약간 나쁨), 월 포함 기준 -0.07~-0.11%p(약간 좋아짐)이고, 부트스트랩 95% 구간이 모두 0을 포함한다.
- HGB에서는 기온을 더하면 **오히려 나빠진다**(+0.73%p, 구간이 0을 포함하지 않음). 약 1년 학습 데이터에서 기온을 넣은 트리 모델이 과적합한 것으로 보인다(원인 확정은 못 함).
- 폴드별로도 일관되지 않다. `cal` 대비 `cal+기온`은 10개월 중 5개월 개선, 5개월 악화다(`daily_total_quantity_by_fold.csv`).
- 대조 실험(기온을 날짜 순서만 어긋나게 바꾼 플라세보 40회): 실제 기온은 플라세보 평균(+0.16%p 악화)보다 약간 낫지만, 절대 크기가 0.1%p 안팎이라 실무적으로 의미가 없다. 생성 규칙의 총량 기온 계수가 ±4.5%로 작고 일별 잡음이 더 크기 때문으로 보인다.
- 주문 수·매출도 같은 결론이다(WAPE 변화 -0.1~+0.2%p, 구간이 0을 포함. 매출은 HGB에서만 악화).
- 월 변수를 추가하면 `cal`보다 오히려 나빠졌다(7.58→8.02%). 이 데이터에서는 월이 요일·학사 변수 이상의 정보를 주지 못하고 잡음만 더한 것으로 해석한다.

| 대상 | 달력만 | 달력+기온 | 달력+월 | 달력+월+기온 |
|---|---|---|---|---|
| HOT WAPE | 75.0% | **17.0%** | 24.5% | **17.6%** |
| ICE WAPE | 51.9% | **17.0%** | 22.2% | **17.1%** |

- **기온은 HOT/ICE 예측을 크게 개선한다.** 월 변수를 이미 포함한 모델 기준으로도 HOT -6.9%p, ICE -5.0%p이며 95% 구간이 0을 포함하지 않는다(HGB도 같은 방향).
- 플라세보 40회에서는 이 개선을 따라간 경우가 0회였다.
- 단, 4절의 설명대로 이 규칙은 데이터 생성 단계에서 주입된 것이다. 실제 판매에서 같은 크기의 효과가 나온다는 뜻이 아니다.

| 모델 | WAPE |
|---|---|
| 같은 요일 8주 평균 | 54.15% |
| GLM 달력 | 51.06% |
| GLM 달력 + 평균기온 | 49.84% |

## 6. 결론

| 질문 | 결론 |
|---|---|
| 과거 유사 기온·요일에 잘 팔린 메뉴를 제시할 수 있는가 | 가능. 모든 구간에서 아메리카노 1위이고, ≤15℃는 따뜻한 커피류, >25℃ 평일·토요일은 복숭아 살구 아이스티가 상위. 표본이 작은 하위 순위는 불안정 |
| 기온에 따른 HOT/ICE 변화를 보여줄 수 있는가 | 가능. ICE 비중 5%(≤0℃) → 88%(>25℃), 50% 교차점 약 15℃. 단 생성 규칙이 주입된 합성 데이터라 실제 고객 행동의 증거는 아님 |
| 기온이 일 총판매량 예측을 개선하는가 | **아니오(측정 불가)**. 304일 검증에서 WAPE 변화가 ±0.1%p 안팎이고 신뢰구간이 0을 포함. HGB는 오히려 악화 |
| 기온이 HOT/ICE 수량 예측을 개선하는가 | **예, 크게**. HOT 75→17%, ICE 52→17% (월 포함 기준 HOT -6.9%p, ICE -5.0%p). 주입된 규칙의 복원 |
| 기온이 메뉴별 판매량 예측을 개선하는가 | **제한적**. 월 변수 없이는 -1.1%p(ICE 전용 음료 중심), 월 변수를 쓰면 이득 없음 |

종합: **날씨(기온)는 "총매출 예측"보다 "HOT/ICE 구성과 ICE 전용 메뉴 수요"를 설명·예측하는 데 쓸모가 있다.** 총판매량 예측은 요일·공휴일·학사 달력이 이미 대부분을 설명하고, 기온을 더해도 개선이 확인되지 않았다. 다만 모든 수치는 합성 데이터에서 나온 것이므로 실제 매출에서의 효과 크기는 **확인되지 않았다.**

## 7. 한계

- 합성 매출이며 날씨 효과가 주입됨 (0절). 효과 크기와 모양은 생성 설정에 의해 정해졌다.
- 날씨 입력이 실제 관측치라 예보 오차가 반영되지 않았다(낙관적 상한).
- 학습 이력이 1~2년뿐이라 월·계절과 기온을 분리하기 어렵다(첫 폴드는 각 월을 1번만 학습).
- 강수량은 396일 결측이어서 사용하지 않았다. 결측의 의미가 확인되지 않아 0으로 채우지 않았다.
- 학사일정은 확정된 일정만 사용했다(미확인 `NaN`은 0이 아니라 정보 없음으로 두고 제외). 한대부고 2025 추정 일정은 효과가 적용되지 않은 것으로 기존 검증에 기록돼 있다.
- 편상관의 p값은 자기상관을 무시한 근사이고, 모델 하이퍼파라미터는 튜닝하지 않았다.
- Prophet 비교는 하지 않았다. 기존 `prophet_validation/`은 별도 가상환경(`.venv`)에서 Prophet을 쓰지만 메인 환경에는 설치돼 있지 않아 새 도구를 들이지 않고 scikit-learn으로 진행했다. 또 `prophet_validation`은 뉴욕 샘플 데이터 기준이며 404다방 데이터와 직접 연결돼 있지 않다.

## 8. 다음 구현 단계 (제안, 미실시)

1. **실제 POS 매출이 확보되면 같은 스크립트를 그대로 재실행**해 효과 크기를 다시 확인한다. 총판매량 개선이 실제로 있는지는 이때 판단한다.
2. 운영 예측에는 기온을 **HOT/ICE 비중 모델의 입력**으로 먼저 도입하고, 총판매량 모델은 달력 변수(요일·공휴일·학사) 중심으로 시작한다. 기온 편입은 실제 데이터로 이득이 확인된 뒤에 한다.
3. 예측 시에는 관측 기온이 아니라 **단기예보 기온**을 쓰므로, 예보 이력을 쌓아 같은 검증을 예보값으로 반복해 예보 오차에 따른 이득 감소를 측정한다(`backend/weatherdata`에 단기예보 수집 코드가 있으나 이번 작업에서는 수정·사용하지 않았다).
4. 강수량 결측의 의미(공란이 무강수인지 미관측인지)를 기상청에 확인한 뒤 강수 변수를 별도로 검증한다.
5. 데이터가 더 쌓이면(2년 이상) 월 변수 없이 기온만 쓰는 모델과 월+기온 모델을 다시 비교한다.
